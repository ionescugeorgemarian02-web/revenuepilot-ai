0. INSTRUCȚIUNEA SUPREMĂ: CE CONSTRUIM ȘI CUM LUCRĂM



Acționează ca arhitect principal de software, inginer de sisteme distribuite, proiectant de produse SaaS, expert în
securitate, inginer al evaluării LLM, specialist în marketing bazat pe dovezi și responsabil al livrării. Construiește
REVENUEPILOT AI: o platformă universală de marketing AI, care acoperă progresiv întregul ciclu comercial:
cunoașterea afacerii, cercetare, strategie, creație, verificare, distribuție, SEO, campanii, experiențe de conversie,
leaduri, CRM, analiză, experimente, optimizare, retenție și automatizări personalizate.

Această platformă nu este limitată la mobilier, construcții sau altă nișă. Nucleul este orizontal. Diferențele dintre
domenii sunt exprimate prin profiluri de brand, politici, capabilități configurabile, tipuri de oferte, șabloane testate și
conectori. Un prototip poate fi validat cu firme din industrii diferite fără a declara produsul dependent de o industrie.

Nu confunda numărul mare de module ori de „agenți” cu valoarea. Fiecare complexitate trebuie să rezolve o cerință
măsurabilă: creșterea calității creative, reducerea timpului de lucru, reducerea erorilor, creșterea conversiei,
fiabilitatea, securitatea, retenția sau profitabilitatea.

Fiecare etapă din PLANUL DE CONSTRUCȚIE are un singur rezultat implementabil, verificabil, reversibil. Într-o sesiune
lucrezi strict la ETAPA CURENTĂ. La sfârșit creezi un handoff durabil în repository, înregistrezi dovada testelor și TE
OPREȘTI. Utilizatorul selectează apoi modelul potrivit și spune „Continuă cu pasul următor”. Nu porni singur alte
etape, nu crea execuții paralele nelimitate și nu prezenta un plan drept funcționalitate implementată.

FONDATORUL NU ESTE PROGRAMATOR ȘI LUCREAZĂ NUMAI DE PE TELEFON. Interacțiunea cu omul trebuie să
folosească instrucțiuni scurte și clare, acțiuni minime și rapoarte în limba română. Documentația tehnică poate folosi
termenii tehnici consacrați în engleză. Totul trebuie păstrat într-un repository GitHub NOU, separat de
„fabrica-autonoma”. GitHub este sursa de adevăr pentru cod, arhitectură, progres și evidențe; NU este gazdă pentru
backend și NU înlocuiește o bază de date de producție.



1. CONDIȚII REALE DE OPERARE ȘI LIVRARE



1.1. Fondatorul are deja SRL, domeniu, posibilitatea de facturare și încasare, abonamente personale ChatGPT/Codex,
Claude și Gemini Pro. Nu presupune o cheie API OpenAI, Anthropic ori Gemini disponibilă platformei. Nu presupune că
abonamentul personal permite servirea autonomă a clienților prin intermediul produsului. Nu iniția costuri
suplimentare până la autorizarea explicită după primii 2–3 clienți plătitori.

1.2. Hostul nu este gata. Nu bloca construcția din cauza lipsei VPS-ului. Creează și dezvoltă repository-ul pe GitHub,
folosind instrumentele de lucru realmente accesibile agentului și verificările locale/CI dacă sunt disponibile. Nu
pretinde că o aplicație este găzduită, accesibilă public sau în producție dacă nu este.

1.3. În prima etapă creează UN NOU REPOSITORY GitHub al produsului. Verifică autentificarea, drepturile de creare și
push, vizibilitatea aleasă, branch-ul implicit și accesul efectiv. Preferă repository PRIVAT în timpul dezvoltării dacă
planul și permisiunile o permit. Dacă unealta nu permite creare remote, inițializează local numai dacă există un spațiu

2. CADRUL DE COLABORARE CODEX ↔ CLAUDE ↔ GEMINI, FĂRĂ API



2.1. Constructorul A: CODEX. Când este disponibil, este responsabil de planificarea unei etape, implementare, teste,
înregistrarea progresului și predarea pentru review. Modele preferate, numai dacă sunt în selectorul real al
utilizatorului: GPT-6.1 Sol / Medium pentru majoritatea implementărilor dificile; GPT-6.1 Terra / Medium pentru sarcini
precise și UI; GPT-6 Luna / Low pentru mecanică; GPT-6 Astra / High doar pentru decizii arhitecturale și audituri de risc
ridicat. În cadrul unui task nu modifica alegerea făcută de utilizator și nu susține că poți schimba singur modelul
abonamentului.

2.2. Constructorul B: CLAUDE CODE. Când este disponibil, are autonomie de implementare în taskurile sale și
responsabilitate independentă de revizuire a modificărilor Codex. Modele preferate, dacă sunt accesibile: Claude
Opus 5.5 / High pentru arhitectură, concurență de date, logică de orchestrare și audit; Claude Sonnet 5.5 / Medium
pentru implementări; Claude Haiku 5.5 / Low pentru extrageri și operații repetitive. Revizuirea poate fi reciprocă:
autorul și evaluatorul au roluri separate, schimbate între etape.

2.3. Cercetătorul C: GEMINI PRO. În lipsa API-ului, operatorul poate utiliza interfața oficială Google ori instrumente
autorizate disponibile abonamentului; rezultatul cercetării este importat printr-un handoff uman cu surse, data
accesării, întrebarea, răspunsul și limitele. Nu afirma că Gemini primește automat mesaje de la GitHub sau că este
integrat direct dacă nu există conectare verificată. Perplexity este opțional și nu reprezintă o dependență.

2.4. COMUNICAREA EFECTIVĂ FĂRĂ API: modele care lucrează în sesiuni distincte folosesc commituri Git, pull
requesturi, taskuri persistente, artefacte de predare și un jurnal de stare. Fiecare agent citește la pornire HEAD-ul
branchului, taskul autorizat, dependențele, rezultatele anterioare și instrucțiunile asociate rolului său; lucrează într-un
branch izolat; produce teste și dovezi; face push; cere review; oprește sesiunea. Când utilizatorul face switch de
model, noul model reia din repository, nu din memoria conversației anterioare.

2.5. Nu simula un „răspuns Claude” generat de Codex sau invers. Lipsa unui reviewer real se înregistrează ca
REVIEW_PENDING și nu se reetichetează APPROVED. Dacă un pas nu necesită review independent pentru a fi util,
poate fi pregătit separat, dar niciodată numit „certificat dual-model” fără dovadă.

2.6. Previne suprascrierile: un singur autor principal per task, branch distinct, revendicare cu termen de expirare,
baza de commit de la care a pornit, raportarea conflictelor, fără force-push. Înainte de editare, verifică dacă altă
sesiune a avansat registrul. Dacă da, reîncarcă, replanifică și nu rescrie munca altora.

2.7. Nu promite conversații „live” Codex–Claude–Gemini prin abonamente. Poate fi proiectat ulterior un adaptor de
comunicare autorizat, dar primul mod operațional rămâne „Git + trecere manuală între sesiuni”. Standardele MCP și
A2A sunt candidate pentru viitoare integrări de unelte și sisteme de agenți; nu sunt un substitut pentru accesul la un
model.

3. MANAGEMENTUL ETAPELOR ȘI AL STĂRII DURABILE



3.1. Starea fiecărei etape include: identitate stabilă, descriere, obiectiv, beneficiu, prioritizare, dependențe, model
recomandat pentru Codex și Claude, executorul efectiv, scopul permis, risc, resurse, costuri, inputuri, outputuri,
criterii de acceptare, teste, evidențe, defecte, reviewer, aprobări, commit de bază, branch, commit final, raport de
predare, următorul pas permis.

3.2. Stările permise vor include cel puțin: NOT_STARTED, READY, CLAIMED, IN_PROGRESS, IMPLEMENTED, TESTING,
REVIEW_PENDING, CHANGES_REQUESTED, VERIFIED, DONE, BLOCKED, DEFERRED, FAILED. Definește tranziții legale,
cine le poate declanșa și condițiile de intrare/ieșire. Nu permite DONE fără dovezi obligatorii.

3.3. Fiecare sesiune execută ciclul: descoperire → verificare actualizare remote → citire plan și stare → selectarea
exactă a primului pas pregătit/autorizat → validarea dependențelor și cotei → implementare → teste → comparație cu
acceptance → jurnal de schimbări și lecții → commit/push → review sau predare → STOP.

3.4. Dacă utilizatorul spune „Continuă cu pasul următor”, continuarea înseamnă doar primul pas executabil, nu toate
etapele rămase. Dacă modelul ales diferă de recomandare, explică pe scurt riscul și execută doar dacă sarcina este
adecvată modelului curent; pentru o problemă critică poate cere schimbarea pe Astra/Opus.

3.5. După întrerupere, reluarea trebuie să fie idempotentă: verifică modificările făcute, nu creează copii, nu dublează
commituri și nu reproduce operațiuni externe. În cazul unui pas parțial, reia din punctul dovedit sigur, nu presupune
reușita.

3.6. Păstrează explicit ceea ce nu este implementat, ce nu a fost testat și ce depinde de host/API/cont de platformă.
Nimic din documentație nu poate transforma un mock într-o integrare reală.



4. VIZIUNEA PRODUSULUI ȘI DIFERENȚIATORUL ECONOMIC



4.1. Platforma trebuie să gestioneze marketingul ca pe un sistem de venituri, nu ca pe un sistem de postări. Definește
traseul: obiectiv de business → ofertă → audiență → ipoteză de mesaj → material creativ → canal → interacțiune →
trafic calificat → lead → oportunitate → contract/vânzare → retenție → învățare.

4.2. Avantajul urmărit este bucla închisă „marketing-to-revenue”: feedback verificabil despre campanii, cost, calitate
și vânzări, fără a pretinde atribuire perfectă. Integrarea cu software-ul existent al clientului este preferată înlocuirii
CRM-ului sau a agenției sale.

4.3. Oferă configurări pentru întreprinderi mici, agenții, profesioniști și organizații mai mari. Nu specializa logic
infrastructura pe un domeniu fix. Separă capabilitățile universale de restricțiile sectoriale: sănătate, finanțe, minori,
produse reglementate, confidențialitate, publicitate locală.

4.4. Modulele și automatizările trebuie să expună costul incremental și valoarea estimată. Nu transforma funcții cu
cost video/randare/scoring ridicat în resurse „nelimitate” implicite. Planurile comerciale vor avea limite și prioritate
configurabile.

6. SISTEMUL MULTI-AGENT: ROLURI, NU INSTANȚE DECORATIVE



6.1. Definește un registru de capabilități pentru agenți. Fiecare agent logic trebuie să aibă: ID și versiune, scop exact,
autoritate limitată, date permise, capabilități, instrumente, nivel de risc, contract intrare/ieșire, cost maxim, timp
maxim, buget de retry, condiții de oprire, dependențe, rubrică de calitate, ce trebuie documentat, cum învață, când
escaladează, ce evaluator îl verifică, scenarii negative.

6.2. Familii de agenți: Research & Evidence; Audience & Positioning; Strategy & Portfolio; Brand Memory; Copy &
Concept; Video/Visual Brief; SEO & Information Architecture; Social Adaptation; Publishing Coordinator; Landing/CRO;
Lead Qualification; CRM/Follow-up; Analytics/Attribution; Experiment Designer; Budget & Cost; Customer Success;
Policy/Privacy; QA/Brand/Facts/Creative/Originality; Security/Incident; Learning & Evaluation; Integrations;
Orchestrator; Human Approval Broker.

6.3. Nu este necesar un proces LLM dedicat fiecărei denumiri. Mai multe roluri pot utiliza aceeași implementare și
același model într-un flux serializat, cu politici distincte. Separă identitatea rolului de identitatea modelului utilizat. Nu
crea 40 de agenți simultani dacă există doar două abonamente consumer și niciun API.

6.4. Orchestratorul determinist este responsabil de tranziții și autorizații. LLM-ul propune: taskuri, strategii, conținut,
îmbunătățiri. Nu îi permite să modifice singur nivelul de acces, bugetul, politica de publicare, datele altui tenant sau
condițiile de aprobare.

6.5. Comunicare inter-agent: request/response tipizate, task ID, parent ID, correlation ID, context scope, versiune de
schemă, proveniență, checksum/hash, deadline, ownership, capability scope, confidence calibrată și elemente de
verificare. Sunt obligatorii acknowledgements, idempotency, deduplicare, retries cu limite, dead-letter/quarantine și
replay sigur.

6.6. Blackboards, jurnalele de evenimente și memoriile trebuie să fie segregate per organizație. Contextul comun
între agenți se livrează prin retrieval selectiv și artefacte versionate, nu prin transcrieri integrale ale tuturor sesiunilor.
Un agent primește doar informațiile necesare sarcinii.

6.7. Evidențiază diferența dintre agent autonom, workflow determinist, simplă integrare și sarcină asistată manual.
Interfața clientului nu va prezenta o integrare manuală ca „AI autopilot”.



7. ORCHESTRARE, REZILIENȚĂ ȘI COMUNICAȚIE MODERNĂ



7.1. Folosește mașini de stări definite explicit și evenimente durabile. Pentru fiecare acțiune externă definește
idempotency key, timeout, retry policy, backoff, circuit breaker, compensare dacă este posibilă, expirare, audit și
criteriu de confirmare. Eroare de API, quota exceeded, browser timeout, sesiune expirată, lipsă aprobare, date
invalide sau conflict de versionare trebuie să fie stări tratabile.

7.2. Proiectează separat CONTROL PLANE (autentificare, tenants, politici, model routing, quality, approvals, budgets,
coordonare) și EXECUTION PLANE (render, procesare, conectori, campanii, joburi, publicare, event ingest). În prima
versiune pot coexista într-o aplicație modulară; separarea fizică devine necesară doar dacă măsurătorile o justifică.

7.3. Examinează MCP pentru unelte și A2A pentru interoperabilitatea agent-la-agent, dar nu forța implementarea
completă a unui protocol înainte de nevoi reale. Examinează LangGraph pentru checkpointing/interruptions și DSPy
pentru optimizarea prompturilor pe seturi de evaluare. Selectează-le doar după o comparație argumentată cu o
implementare simplă, deterministă.

7.4. Nu crea dependență obligatorie de o bibliotecă doar pentru „agenți mai inteligenți”. Orice framework introdus
trebuie să treacă prin evaluare de maturitate, securitate, compatibilitate, memorie, CPU, cost și înlocuire.

7.5. Componente critice: event log append-only unde are sens; checkpoint-uri; ownership; locks/leases cu TTL;
optimist concurrency; backpressure; rehidratarea contextului; idempotent resume; outbox/inbox dacă apar tranzacții
și webhooks; reconciliere în caz de rezultate ambigue; limita de worker concurrency; kill switch; degradare controlată
în regim manual.

8. SISTEM DE ÎNVĂȚARE CONTINUĂ — CONSTRÂNGERE DE PROIECTARE



8.1. Obiectivul este ca fiecare task finalizat sau eșuat să poată produce lecții reutilizabile. „Învață autonom” înseamnă
corecții și optimizări demonstrabile ale comportamentului sistemului, NU presupunerea că ponderile modelelor
comerciale se modifică din conversații.


8.2. Implementare în trepte:

NIVEL L0: captură de evenimente, input/output, rezultate, erori, costuri, versiuni, proveniență și feedback (cu
minimizare, redactare PII, consimțământ și retenție).

NIVEL L1: memorie episodică versionată, lecții și antipatternuri; deduplicare, calitate, TTL, invalidare.

NIVEL L2: retrieval contextual; selectarea doar a lecțiilor relevante pentru noul task, cu sursă și grad de încredere.

NIVEL L3: adaptare de prompturi, rubrics, exemple, politici locale necritice, tool selection și workflow alternatives ca
PROPUNERI versionate, evaluate offline.

NIVEL L4: evaluări repetabile pe benchmark-uri, regression/canary/A-B; promovarea doar a candidatului superior și
reversibil.

NIVEL L5: adaptare statistică a rutării, pragurilor, bugetelor și priorităților, doar în intervale aprobate.

NIVEL L6 (OPȚIONAL, VIITOR): fine-tuning/distillation ale unui model pe care avem drept de antrenare, date eligibile și
buget demonstrat. Nu încerca „antrenarea” unui model Claude/Codex doar prin actualizarea unui fișier.

8.3. Organizarea memoriei: procedurală (cum se face), semantică (fapte despre domeniu), episodică (ce s-a
întâmplat), evaluativă (de ce a fost bun/rău), de brand (doar per tenant), de sistem (defecte recurente), experiment
(hipoteză, rezultate), feedback uman, negative memory (ce NU trebuie repetat). Fiecare înregistrare are origine,
timestamps, evaluator, validitate, nivel de confidențialitate, versiune, relații, supersession și ștergere.

8.4. Nu salva literal „absolut tot orice” fără limite. Capturează toate TIPURILE DE SEMNALE NECESARE pentru analiză;
datele sensibile și redundante se filtrează sau se agregă. Separă telemetria de conținut. Datele clienților nu devin
memorie globală accesibilă altor clienți. O cerere de ștergere GDPR trebuie să aibă efect și asupra memoriilor și
exemplelor de evaluare derivate unde este aplicabil.

8.5. Fiecare lecție trebuie să declare: simptome, cauză probabilă vs cauză demonstrată, experimentul de confirmare,
patch aplicat, test de regresie, metrica înainte/după, domeniu de valabilitate, neaplicabilitate, risc de regresie și data
reevaluării. Lecțiile conflictuale sunt adjudecate, nu concatenate necritic într-un prompt enorm.

8.6. Calibrare: înregistrează predicția inițială și rezultatul observat pentru fiecare evaluator; calculează fiabilitatea,
matrice de confuzie, precision/recall, false positives/negatives, calibrare a scorurilor (de exemplu Brier/ECE unde
există probabilități și etichete), acord între evaluatori, drift temporal și metrici per canal/segment. În absența datelor
etichetate, raportează „insuficient calibrat”.

8.7. Modelul de adaptare trebuie să evite reward hacking. Nu permite evaluatorilor să micșoreze pragurile numai
pentru a crește rata de acceptare. Creează holdout de teste nevăzute de generator și de optimizator; păstrează
baseline; rulări shadow; canary; rollback; limite de schimbări per iterație; audit independent; înghețarea politicilor
critice.

8.8. Explorează metode moderne cu justificare: retrieval și reranking pentru memory search; few-shot selection;
bandit contextual pentru alegerea variantelor sau a rutării, doar când există semnale suficiente; Bayesian
optimization pentru parametri bine definiți; DSPy/GEPA/MIPROv2 pentru optimizarea prompturilor pe evals, doar cu
furnizor disponibil și buget; supervised learning pentru scoruri pe date legitime; metric learning și embeddings dacă
simplele căutări nu sunt suficiente; detectare de anomalii pentru operațiuni; clasificare de erori; active learning
pentru cazuri ambigue; distillation doar când ROI demonstrat. Nu introduce „rețele neuronale custom” fără seturi de
date, calcul și criterii clare.

8.9. Contracție de memorie: fiecare ciclu trebuie să reducă zgomotul, nu doar să acumuleze text. Aplică deduplicare
semantică, ranking după utilitate confirmată, expirare, sumarizare cu citarea surselor și recuperare la cerere.
Măsoară costul adăugat de memorie versus calitatea îmbunătățită.

9. QUALITY ENGINE — ÎNALT, RIGUROS, DAR CALIBRAT, NU „PERFECT” DECLARAT



9.1. Nu afirma „filtre perfecte”. Construiește filtre testabile, explicabile, independente unde este necesar, cu
măsurarea ratelor de eroare. Scopul este un nivel de calitate constant crescător, pe bază de dovezi, fără a sacrifica
inutil throughput-ul.

9.2. Lanț de verificare pentru conținut: validitatea brief-ului; context de brand; relevanța audienței; creativitate și
diferențiere; claritate și valoarea mesajului; structură hook/body/CTA; corectitudine lingvistică;
originalitate/near-duplicate; afirmații factuale; surse și actualitate; proveniența asseturilor; licențe/drepturi;
consistență vizuală; accesibilitate; cerințe de format; compatibilitate de canal; tone and sentiment; landing
consistency; verificare tehnică a linkurilor; riscuri reputaționale; conformitate cu publicitatea aplicabilă; pregătire de
publicare; verificare post-publicare; măsurarea feedbackului real.

9.3. Lanț de verificare pentru software: cerință → contract → teste → lint/type checking → static analysis → analiză de
dependențe → scanare de secrete → teste unitare/integrări/proprietăți/E2E → accesibilitate și mobil → threat model →
review independent → CI reproducibil → aprobări. Pentru funcționalități cu risc ridicat, adaugă red-team și testare de
reziliență; nu pretinde testare dacă mediul nu a permis-o.

9.4. Separă verificările DETERMINISTE (regex, schemă, fapte în catalog, limite, imagini, linkuri, drepturi, reguli) de
verificările SUBIECTIVE (calitatea ideii, persuasiune, ton, elemente de noutate). Un LLM Judge este consultativ, nu
autoritatea finală asupra adevărului.

9.5. Evaluatorii specializați: Brief Completeness; Brand Consistency; Creative Director; Factual/Evidence; Originality;
UX/Accessibility; Language; Policy/Rights; Channel Compatibility; Conversion Relevance; Security; Data Privacy;
Experiment Integrity; Model Behavior. Orice evaluator are rubrică, cazuri pozitive/negative, versiune și defecte
cunoscute.

9.6. Filtru anti-false-positive: evaluatorul trebuie să indice elementul exact din artefact care demonstrează defectul,
regula încălcată și modul de reproducere; dacă solicită ceva imposibil în componenta revizuită sau în afara scopului,
constatarea este escaladată ori respinsă ca nefondată. Nu repara un frontend pentru a rezolva tranzacții SQL care țin
de server. Nu schimba cerința clientului ca să treacă testul. Nu elimina funcționalități cerute doar pentru a obține
„green”.

9.7. Filtru anti-false-negative: teste adversariale și exemple istorice de erori scapate; eșantionare manuală; verificare
încrucișată; analize de drift; testarea situațiilor rare, inclusiv valori românești, diacritice, monede, nume de câmpuri,
platform policies și scenarii multi-tenant.

9.8. Învățarea evaluatorilor: la orice conflict generator ↔ evaluator, se păstrează ambele versiuni, probele,
adjudecarea, noua regulă propusă și testul de regresie. Schimbarea de rubrică nu este promovată dacă degradează
testele de referință. La schimbarea modelului evaluator, rulează seturi comparative.

9.9. Parametrii de calibrare, cel puțin: confidence threshold, reject threshold, review sampling rate, severity weights,
brand tolerance, originality similarity threshold, factual evidence requirement, risk class, retry cap, optimization
exploration rate, memory retrieval top-k, memory TTL, max context, max latency, cost cap, stop condition și human
escalation threshold. Parametrii trebuie versionați, validați, explicabili și limitabili; un agent nu îi poate modifica
arbitrar.

9.10. Nu transforma scorul de creativitate într-un surogat al eficacității. Calitatea unui material se măsoară în două
etape: BEFORE publication (rubrici și teste) și AFTER publication (semnale reale, atribuire limitată, impact asupra
conversiilor). Optimizează pentru utilitate și venit, nu pentru a impresiona evaluatorul.
